# Running and operating AltQueue

## Requirements and build

Use the Go version in `go.mod`. The checked-in Protobuf code means no generator is required for normal development.

```sh
go mod download
go build -o bin/altqueued ./cmd/altqueued
go build -o bin/altqueue ./cmd/altqueue
```

On Windows, add `.exe` to binary output names, or use `go run ./cmd/altqueued` and `go run ./cmd/altqueue` directly.

## Local development

Terminal one:

```sh
go run ./cmd/altqueued -data ./data
```

Terminal two:

```sh
go run ./cmd/altqueue create emails
go run ./cmd/altqueue publish emails "hello"
go run ./cmd/altqueue work emails
```

Alternatively, run `go run ./examples/producer`, then `go run ./examples/worker`. The producer creates the `examples` queue; the worker uses automatic heartbeat renewal and four processing goroutines.

The `work` CLI is only a print-and-ack demonstration, not an application job handler. CLI JSON payloads are base64 encoded; `work` prints the payload bytes as text.

## Broker flags

| Flag | Default | Meaning |
| --- | --- | --- |
| `-data` | `data` | Pebble data directory |
| `-listen` | `127.0.0.1:7331` | gRPC listener |
| `-http` | `127.0.0.1:7332` | Operational HTTP listener |
| `-tls-cert` / `-tls-key` | empty | PEM server certificate and private key; both required together |
| `-allow-insecure-remote` | false | Unsafe remote-development override; never a production default |
| `-backup-to` | empty | Open the data directory, checkpoint to a new path and exit; stop the normal broker first |

The data directory must be on supported persistent local storage and owned by one process. Opening an already-owned directory fails. Do not share it between brokers or mount the same live directory on several nodes.

## Token authentication

Set the same random token in the broker and client environments. Tokens must contain at least 16 bytes; prefer 32 or more randomly generated bytes. Do not commit the token or pass it in a CLI argument.

PowerShell:

```powershell
$env:ALTQUEUE_TOKEN = "replace-with-a-long-random-secret"
```

Bash:

```sh
export ALTQUEUE_TOKEN='replace-with-a-long-random-secret'
```

Set this in every terminal used for the broker or CLI. Token authentication covers all gRPC operations and `/metrics`. Health and readiness expose only simple status. A shared token is not per-user or per-tenant authorization.

## TLS

Remote listeners require TLS and a token. For development only, an OpenSSL self-signed certificate can be generated with a SAN matching the client's hostname:

```sh
openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt -days 365 -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

Run with the token already configured:

```sh
go run ./cmd/altqueued -tls-cert server.crt -tls-key server.key
go run ./cmd/altqueue -ca server.crt create secure-jobs
```

With a publicly trusted certificate, use the CLI's `-tls` flag instead of `-ca`. The optional `-server-name` flag controls certificate hostname verification; do not disable verification. Issue certificates with the correct remote hostname/IP SANs for real deployments.

The operational listener uses HTTPS when TLS is configured. Protect certificate and data files with deployment-appropriate permissions. Token rotation currently requires restarting the broker and updating clients.

## CLI commands

Connection flags precede the command. Command flags precede the queue and other positional arguments:

```sh
altqueue -addr 127.0.0.1:7331 create -max-jobs 1000 -max-bytes 10485760 -max-in-flight 10 -max-attempts 5 -retry-base 1s -retry-max 1m jobs
altqueue publish -delay 2s jobs "one" "two"
altqueue fetch -limit 10 -lease 30s -wait 5s jobs
altqueue ack jobs "JOB_ID" "LEASE_TOKEN"
altqueue nack -reason "temporary failure" jobs "JOB_ID" "LEASE_TOKEN"
altqueue nack -permanent -reason "invalid input" jobs "JOB_ID" "LEASE_TOKEN"
altqueue extend -duration 30s jobs "JOB_ID" "LEASE_TOKEN"
altqueue queues -limit 100
altqueue stats jobs
altqueue dead -limit 100 jobs
altqueue requeue jobs "DEAD_JOB_ID"
altqueue delete jobs
```

Delete only works for empty queues. Manual dead-letter requeue resets attempts but preserves the job ID and payload. Dead jobs are never silently removed and still consume queue capacity.

Lease extension requests a remaining window from now and never shortens the current deadline. Expired leases cannot be revived. The scheduler reclaims in-flight slots; a deadline passing does not immediately remove its lease entry before the scheduler runs.

## Health, metrics and logs

- `GET /healthz`: process is responding.
- `GET /readyz`: engine is available and broker is accepting work.
- `GET /metrics`: aggregate RPC counters/latency, job-state gauges and Go/process metrics.

Use `Authorization: Bearer TOKEN` for metrics when authentication is enabled. Metrics do not include payloads or high-cardinality job identifiers. Logs are structured with `slog`; the broker does not log tokens or job payloads.

## Graceful shutdown and recovery

Send Ctrl+C, SIGINT, or SIGTERM where supported. The broker stops admission, cancels long polls, drains gRPC requests within a 10-second deadline, closes HTTP and then closes Pebble. Outstanding leases remain durable.

After an unclean exit, reopen the same directory. Ready ordering, delayed jobs, dead-letter jobs and unexpired leases are recovered. Due delayed jobs and expired leases are processed by the scheduler. Acknowledged completions remain removed.

A storage commit error makes the engine unready and stops normal operations. The process exits through the scheduler error path; inspect storage before restarting. Never delete the directory as an automatic repair action.

## Backup and restore

Stop the normal broker, then create a checkpoint at a destination that does not already exist:

```sh
altqueued -data ./data -backup-to ./backups/checkpoint-001
```

The engine API also supports a consistent checkpoint while an embedded engine is open, but no remote backup RPC is exposed. Do not copy an arbitrary set of live Pebble files.

To restore, stop the broker, preserve the original directory separately, copy the complete checkpoint to a new data directory, and start with `-data` pointing to that copy. Never overwrite a running database.

Restoring an old checkpoint loses later publications and can replay previously completed work. Checkpoints on the same disk are not protection against that disk's loss; copy completed backups to independent storage.

## Docker

A multi-stage Dockerfile is supplied. Build it in a Docker-enabled environment:

```sh
docker build -t altqueue .
```

Local-only development example (the unsafe flag is explicit because the container must listen on non-loopback addresses):

```sh
docker run --rm -p 127.0.0.1:7331:7331 -p 127.0.0.1:7332:7332 -v altqueue-data:/var/lib/altqueue altqueue -listen 0.0.0.0:7331 -http 0.0.0.0:7332 -allow-insecure-remote
```

For remote deployments, mount certificates read-only, set `ALTQUEUE_TOKEN`, omit the unsafe override, and configure both TLS flags. The container runs as a non-root user; verify volume ownership and certificate readability.

### Windows with WSL2

Docker can be used from WSL even when `docker` is not available in Windows PowerShell. Open Ubuntu:

```powershell
wsl.exe -d Ubuntu
```

Then run the build and local development container from the WSL terminal:

```sh
cd /mnt/d/projects/altqueue
docker build -t altqueue .
docker run --rm --name altqueue-dev -p 127.0.0.1:7331:7331 -p 127.0.0.1:7332:7332 -v altqueue-data:/var/lib/altqueue altqueue -listen 0.0.0.0:7331 -http 0.0.0.0:7332 -allow-insecure-remote
```

Adjust the mounted project path if your checkout is elsewhere. In another WSL terminal, the image's bundled CLI can be used directly:

```sh
docker exec altqueue-dev altqueue create emails
docker exec altqueue-dev altqueue publish emails "hello from Docker"
docker exec -it altqueue-dev altqueue work emails
# Stop the worker with Ctrl+C, then stop the broker:
docker stop altqueue-dev
```

The named `altqueue-data` volume survives container removal. Do not remove it unless you intend to delete stored jobs. The local smoke run verified restart/crash recovery, authentication, metrics and non-root volume access; see [implementation status](IMPLEMENTATION.md#docker-validation-in-wsl2).

## Performance and deployment caveats

Payloads currently remain in memory. Logical payload limits do not account for all Go/Pebble overhead or request copies. Requests and long polls have separate admission ceilings, and TCP connections/messages are bounded, but deployment memory limits still need load validation.

Do not fill the data volume: disk-headroom admission is not implemented. Reserve space for WAL files, compaction and checkpoints. Full-disk failures fail closed; they are not a substitute for monitoring free space.

Run the [local benchmark](../benchmarks/queue_test.go) with hardware and commit details recorded. There is no published throughput SLA, replication, failover, multi-tenant isolation, or production certification.
